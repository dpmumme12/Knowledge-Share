# API Reference

Knowledge-Share's JSON API surface is implemented with **Django REST
Framework** and lives alongside the template-rendered pages, under an
`api/` sub-path of each owning app. All endpoints below use
`SessionAuthentication` (the browser session cookie from the template-based
login flow) — there is no separate token/API-key auth mechanism.

A live, generated OpenAPI 3 schema for the `social` app's endpoints is
available at the `social:openapi-schema` route (see below) and is the
authoritative machine-readable contract; this document is the human-readable
companion.

## Social app — `/social/api/...`

Defined in `KnowledgeShare/social/urls.py`, implemented in
`KnowledgeShare/social/api/views.py`, serialized by
`KnowledgeShare/social/api/serializers.py`.

### `GET /social/api/following/<int:pk>`

**View**: `FollowingListView` (`ListAPIView`)
List the users that user `pk` is following.

- **Auth**: none enforced at the view level (readable by anonymous visitors);
  when the requester is authenticated, each result is annotated with
  `is_following` (whether the *requester* follows that user).
- **Response**: array of `UserFollowSerializer` objects —
  `{ id, username, first_name, last_name, profile_image, is_following }`.

### `GET /social/api/followers/<int:pk>`

**View**: `FollowerListView` (`ListAPIView`)
List the users following user `pk`. Same response shape and auth behavior as
`following` above (`UserFollowSerializer`).

### `POST /social/api/follow-unfollow/<int:pk>`

**View**: `FollowUnfollowView` (`GenericAPIView`)
Toggles the requesting user's follow relationship with user `pk`: unfollows if
already following, otherwise follows and creates a `Notification` for the
target user.

- **Auth**: `SessionAuthentication` + `IsAuthenticated` — **required**.
- **Request body**: none required (action is fully determined by the URL `pk`
  and the current session user).
- **Response `201 Created`**: `FollowUnFollowSerializer` —
  `{ user_id: int, is_following: boolean }` (the resulting state).
- **Error `500`**: on any failure, the view logs the exception via
  `logger.exception(...)` through the application's standard `logging`
  pipeline and raises a DRF `APIException` with the fixed message
  *"Unable to process the follow/unfollow request."* — no raw exception text
  is returned to the client, per [[dec-error-logging-reuses-existing-pipeline]].

### `GET /social/api/notifications` / `DELETE /social/api/notifications`

**View**: `NotificationsListView` (`ListAPIView`)

- **Auth**: `SessionAuthentication` + `IsAuthenticated` — **required**.
- **`GET`**: lists the requesting user's notifications, newest first
  (`-created_on`), paginated with `SmallResultSetPagination`. As a side
  effect, marks all currently-unseen notifications for that user as `seen`.
  Response items: `NotificationsSerializer` —
  `{ id, message, user, seen, created_on }`.
- **`DELETE`**: expects a `pk` query parameter identifying the notification to
  delete; deletes it and returns `204 No Content`.

### `GET /social/api/messages` / `POST /social/api/messages`

**View**: `MessagesListView` (`ListAPIView` + `CreateModelMixin`)

- **Auth**: `SessionAuthentication` + `IsAuthenticated` — **required**.
- **`GET`**: requires a `username` query parameter identifying the other
  party in the conversation. Marks that conversation's unread messages
  addressed to the requester as read, then returns the full conversation
  between the requester and `username`, newest first
  (`-message_sent_date`), paginated with `SmallResultSetPagination`.
  Response items: `MessagesSerializer` —
  `{ sender, recipient, content, message_sent_date }`.
- **`POST`**: creates a new `Message` (standard DRF `CreateModelMixin`
  behavior against `MessagesSerializer`).

### `GET /social/api/openapi`

DRF's `get_schema_view(...)`, generated by `ServerSchemaGenerator`
(`KnowledgeShare/utils/api/schema_generators.py`), titled
*"KnowledgeShare.Social"*. Returns the OpenAPI 3 schema document (with a
`servers` entry pointing at `http://knowledge-shared.com`) describing every
view registered under `social/urls.py`.

## Article feed app — `/articlefeed/api/...`

Defined in `KnowledgeShare/articlefeed/urls.py`, implemented in
`KnowledgeShare/articlefeed/api/views.py`, serialized by
`KnowledgeShare/articlefeed/api/serializers.py`.

### `GET /articlefeed/api/articlefeed`

**View**: `ArticleFeedListView` (`ListAPIView`)
Returns published articles across all users, excluding the requester's own
articles when authenticated, newest-updated first.

- **Auth**: none enforced at the view level (readable by anonymous visitors).
- **Filtering**: `django_filters.rest_framework.DjangoFilterBackend` with
  `ArticleFeedFilter` (`KnowledgeShare/articlefeed/filters.py`) — supported
  query params:
  - `search_query` — full-text + trigram search over `title`/`content`
    (delegates to `knowledgebase.helpers.article_fulltext_search`).
  - `min_date` / `max_date` — filters on `updated_on` (`gte`/`lte`).
  - `author` — multi-select of users the *requester* follows (anonymous
    requesters get an empty author list).
- **Pagination**: `SmallResultSetPagination` (page size 15, `page_size`
  query param, max 1000).
- **Response**: array of `ArticleFeedSerializer` objects —
  `{ id, username, full_name, profile_img, title, truncated_content, updated_on }`
  (`username`/`profile_img`/`full_name` resolve to `null`/`''` when the
  article has no author, e.g. the author account was deleted — `author` uses
  `on_delete=SET_NULL`).

## Shared API infrastructure

- **Pagination**: `KnowledgeShare/utils/api/pagination.py` —
  `SmallResultSetPagination(PageNumberPagination)`, page size 15,
  `page_size_query_param='page_size'`, `max_page_size=1000`. Used by every
  paginated endpoint above.
- **Schema generation**: `KnowledgeShare/utils/api/schema_generators.py` —
  `ServerSchemaGenerator` adds a `servers` block to the generated OpenAPI
  document; `RequestResponseSchema` (via the `SerializerSchemaMixin` used by
  `FollowUnfollowView`) lets a view declare distinct `request_serializer` and
  `response_serializer` classes for accurate schema generation when the
  request and response shapes differ.
